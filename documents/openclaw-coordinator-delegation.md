# 4단계: coordinator 연결과 factory-operations 위임

이 문서는 총괄 비서(`coordinator`)가 계근 API를 직접 호출하지 않고 공장 운영
비서(`factory-operations`)에 조회를 위임하는 구성의 설계, 권한, 등록 절차, 검증
계획을 설명한다. 3단계 내용은 [openclaw-factory-tools.md](openclaw-factory-tools.md)에 있다.

## 0. 현재 상태

**로컬 읽기 전용 위임 MVP 검증 완료.** 범위는 한 대의 개발 PC와 비어 있는 개발 DB에서의
읽기 전용 조회 위임이다. 운영 배포나 전체 보안 검증이 끝난 것은 아니다. 확인된 것과
확인되지 않은 것은 6~8절에, 남은 한계와 후속 과제는 9절에 있다.

| 항목 | 상태 |
|---|---|
| 위임 방식 조사와 설계 | 완료 |
| 두 비서의 업무지침(`AGENTS.md`) 수정 | 완료 |
| coordinator 등록, 도구 정책, 에이전트 간 허용 목록 적용 | 완료(2026-10-07, `config validate` 통과) |
| 위임 전용 세션 생성 | 완료. 실제 키는 `agent:factory-operations:delegation` |
| 1차 실제 위임 대화 검증(2026-10-08) | 완료. 통과 항목과 보완 4건은 6절 |
| 1차 검증에 따른 업무지침 보완 | 완료(요청 ID 세션 표식, 재조회 금지, 과거 결과 미전달, 추측 금지) |
| 보완 후 재검증(2026-10-08) | 완료. 3건 통과, 요청 ID 세션 표식은 중복되어 실패(7절) |

코드를 읽어 확인했지만 실제로 실행해 확인하지는 않은 것이다. 실행해 확인한 결과는 6절, 7절, 8절에 따로 적었다.

## 1. 위임 방식

OpenClaw 2026.9.8이 지원하는 비서 간 위임은 두 가지다.

| 방식 | 동작 | 판단 |
|---|---|---|
| `sessions_spawn` + `agentId` | 대상 비서 아래에 하위 세션을 새로 만든다 | 쓰지 않음 |
| `sessions_send` | 대상 비서의 기존 세션에 메시지를 보내고 답을 기다린다 | **채택** |

- **`sessions_spawn`을 쓰지 않는 이유**: 요청자에게 제한적인 허용 목록이 있으면 하위
  세션이 요청자의 실효 도구 목록을 물려받는다(설치된 코드의 `inheritedToolPolicy`).
  `factory-operations` 하위 세션이 계근 도구를 쓰려면 coordinator도 그 도구를 가져야
  하므로 "coordinator는 계근 API를 직접 호출하지 않는다"와 맞지 않는다.
- **`sessions_send`를 쓰는 이유**: 대상 비서 자신의 도구 정책으로 실행되고, 전송 경로에
  도구 상속이 없다. 수신 쪽에는 사용자 지시가 아닌 세션 간 메시지로 표시된다.

```
사용자 ──► coordinator ──(sessions_send)──► factory-operations ──(Tool Search)──► factory-api MCP ──► FastAPI
              도구 1개                          조회 도구 3개                          GET 전용
```

### 응답이 돌아오는 경로

포함 문서(`docs/concepts/session-tool.md`)와 코드로 확인한 동작이다.

- 대상의 답은 요청자에게 **한 번만** 전달된다. 요청자의 응답을 대상에게 되돌려 보내는
  단계가 없고 대상 쪽에 announce 차례도 생기지 않는다. 자동 왕복은 없다.
- 이전 버전의 왕복 횟수 설정(`session.agentToAgent.maxPingPongTurns`)은 이 버전에서
  폐기된 설정이다. 설정 스키마에 없고 마이그레이션 때 제거된다.
- 대기 시간 안에 답이 오면 도구 결과로 바로 돌아온다(`status: "ok"`, `runId`, `reply`).
- 대기 시간을 넘기면 도구 결과는 `status: "accepted"`, `delivery.status: "pending"`이고,
  그 뒤 백그라운드에서 추가로 `min(대기 시간, 60초)` 동안 대상의 실행을 지켜본다. 그
  안에 답이 오면 요청자 세션에 새 차례가 한 번 생기고, 답 본문과 함께 "이전
  `sessions_send` 요청의 결과이며 한 번만 전달된다"는 안내가 붙는다. **[미검증]**
- 늦게 온 답의 본문에는 `runId`나 원래 질문이 들어 있지 않다. 어느 요청의 답인지
  플랫폼이 표시해 주지 않으므로 3절의 요청 ID 규칙을 쓴다.
- 요청자 쪽에 생기는 늦은 결과 차례에서도 `sessions_send`를 쓸 수 있다. 모델이 다시
  보내는 것을 플랫폼이 막지는 않는다.

## 2. 권한

### 적용한 설정 (`~\.openclaw\openclaw.json`의 해당 부분)

```json5
{
  tools: {
    agentToAgent: { enabled: true, allow: ["coordinator", "factory-operations"] },
  },
  agents: { entries: {
    coordinator: {
      workspace: "~/.openclaw/workspace-coordinator",
      tools: {
        profile: "messaging",
        allow: ["sessions_send"],
        deny: ["factory-api__*"],
        codeMode: false,
        loopDetection: { enabled: true },
      },
    },
    // factory-operations와 main은 3단계 설정 그대로
  } },
}
```

- coordinator의 허용 도구는 `sessions_send` 하나다. 파일, 실행, 웹, 메시지 발송,
  하위 세션 생성, 세션 목록·기록 조회는 허용 목록에 없다. `main`의 넓은 권한(전역
  `full` 프로필)을 복사하지 않았다.
- 등록에 `--role coordinator`를 쓰지 않았다. 역할 템플릿이 자체 지침과 위임 설정을
  넣기 때문이다.
- `factory-operations`는 3단계 그대로다(조회 도구 3개, Code Mode 끔, 합계 계산 금지).
- `tools.sessions.visibility`와 `tools.toolSearch`는 건드리지 않았다(기본값).

### main의 교차 비서 접근

적용 전에는 `tools.agentToAgent`가 설정돼 있지 않았다. 코드상 `enabled`는 false가
아니면 켜짐이고 `allow`가 비어 있으면 모든 비서가 허용이다. `main`은 전역 `full`
프로필이라 세션 도구를 모두 가지므로, 다른 비서의 세션에 메시지를 보내고 기록을 읽을
수 있는 조건이었다. `allow`에 두 비서만 넣어 `main`의 다른 비서 접근을 막았다.
`main` 자신의 세션 간 접근은 그대로다. **[미검증]**

### 정책으로 강제되는 것과 지침 수준

에이전트 간 정책(코드의 `createAgentToAgentPolicy`)은 같은 비서끼리는 항상 허용하고,
다른 비서 사이는 양쪽 ID가 모두 `allow`에 있을 때만 허용한다.

| 시도 | 결과 | 강제 수준 |
|---|---|---|
| coordinator → `factory-operations` | 허용 | 정책 |
| coordinator → `main`, 목록에 없는 다른 비서 | 거부 | 정책 **[미검증]** |
| `main` → 다른 비서 | 거부 | 정책 **[미검증]** |
| coordinator → 호출 중인 자기 세션(대기 시간 0 아님) | 거부 | 정책(코드) **[미검증]** |
| 존재하지 않는 임의 세션 키(메인 세션 제외) | 오류. 세션을 만들지 않음 | 정책(코드) **[미검증]** |
| 계근 도구 직접 호출, 하위 세션 생성, 세션 목록·기록 조회 | 도구가 없음 | 정책 **[미검증]** |
| coordinator → 자기 세션(대기 시간 0), 자신의 다른 세션 | 허용됨 | **지침으로만 금지** |
| `factory-operations`의 다른 기존 세션, `label` 지정 | 허용됨 | **지침으로만 금지** |
| 위임 전용 세션만 사용 | | **지침** |
| 요청 ID 부여, 요청 세션 전달과 반환, 두 값의 대조 | | **지침** |
| 대기 중인 요청이 있을 때 세션을 초기화하지 않음 | | **지침**(운영 규칙) |
| 요청당 위임 1회, 자동 재시도 금지, 대기 중 위임 1건 | | **지침** |
| `factory-operations`의 오류 후 자동 재조회 금지 | | **지침** |
| 과거 요청의 결과를 이번 답에 끌어오지 않음 | | **지침** |
| 늦은 결과를 한 번만 전달, 결과를 섞지 않음 | | **지침** |
| 대기 시간 60초 | | **지침**(모델이 고르는 인자) |

**한계**: 요청 ID와 요청 세션의 전달·대조, 전용 세션 사용, 위임 횟수, 재시도·재조회 금지, 중복 전달
방지는 업무지침으로만 지켜지며 코드나 설정으로 강제되지 않는다. 모델이 지침을 따르지
않으면 막을 수단이 없다. 위임 전용 세션은 모든 coordinator 세션이 함께 쓰는 **공유
세션**이라 `factory-operations`가 이전 요청을 기억한다. 과거 결과가 답에 섞이지 않게
하는 것도 지침에만 의존한다.
`loopDetection`은 같은 도구 호출이 반복되는 것을 탐지하는 보조 장치이고, 위 규칙을
대신하지 않는다. 실제 효과는 **[미검증]** 이다.

## 3. 운용 규칙 (업무지침에 반영)

### 위임 전용 세션

- 직접 대화와 위임을 분리하기 위해 `factory-operations`에 전용 세션을 둔다.
- 세션 키는 `agent:factory-operations:delegation`이다. 5.1절의 명령으로 생성한 뒤
  세션 목록과 세션 기록에서 실제 키를 확인했다.
- `sessions_send`가 없는 세션을 자동으로 만드는 것은 비서의 메인 세션 키뿐이다(코드의
  `isConfiguredAgentMainSessionKey`). 전용 세션은 운영자가 미리 한 번 만들어야 한다.
- 이 세션은 모든 coordinator 세션이 함께 쓴다. `factory-operations`는 이 세션에 쌓인
  이전 요청을 기억하므로, 각 위임을 독립적으로 처리하고 과거 결과를 끌어오지 않게
  지침으로 정했다.

### 요청 ID와 요청 구분

요청은 요청 ID 하나가 아니라 **(요청 세션, 요청 ID) 쌍**으로 식별한다.

- **요청 ID**: 형식은 `REQ-YYYYMMDD-NNN`이다. 날짜는 한국 시간이다. `NNN`은 같은
  대화에서 이미 쓴 가장 큰 순번에 1을 더한 세 자리 수다. 같은 대화에서 한 번 쓴 ID는
  다시 쓰지 않는다. 다른 대화에서는 같은 ID가 쓰일 수 있다.
- **요청 세션**: 위임을 보낸 coordinator 세션의 실제 세션 키다(예:
  `agent:coordinator:<세션>`). 모델이 만들지 않고 플랫폼이 가진 값을 쓴다.
  - coordinator는 시스템 프롬프트의 `Runtime:` 줄에 있는 `session=` 값을 그대로 옮겨
    위임 메시지 둘째 줄(`요청세션: …`)에 적는다. 값을 찾을 수 없으면 추측해서 만들지
    않고, 위임하지 않은 채 그 한계를 사용자에게 알린다.
  - `factory-operations`는 세션 간 메시지 머리말에 플랫폼이 붙이는 `sourceSession`을
    기준으로 삼는다. 답의 첫 줄에 요청 ID, 둘째 줄에 `sourceSession`에서 옮긴 요청
    세션을 적는다. 본문의 `요청세션:` 값이 `sourceSession`과 다르거나 없으면
    `sourceSession`을 따르고 셋째 줄에 불일치를 적는다.
  - coordinator는 돌아온 요청 ID와 요청 세션을 모두 대조한다. 하나라도 없거나 다르면
    그 요청의 결과로 쓰지 않고 사용자에게 알린다. 늦게 도착한 결과도 같다.
- 두 값이 같은 출처라는 근거: 실제 실행 기록에서 coordinator 프롬프트의 `session=`
  값과 `factory-operations`가 받은 `sourceSession`이 문자 단위로 같았다(7절). 설치된
  코드에서는 `buildRuntimeLine`과 `buildInterSessionPromptContext`가 각각 이 값을 넣는다.
- 기록을 사후에 추적할 때의 기준 값은 플랫폼의 `runId`다. `sessions_send`의 반환값에
  들어 있고 `factory-operations` 쪽 실행 기록의 실행 ID와 같다. 호출마다 새로 만들어져
  유일하다. 다만 `factory-operations` 모델에게는 전달되지 않고 늦게 도착한 답에도 붙지
  않아, 비서 사이의 대조에는 쓸 수 없다.

이 방식으로 바꾼 경위는 다음과 같다.

| 방식 | 결과 |
|---|---|
| 순번만 쓴 ID(`REQ-YYYYMMDD-NNN`) | 1차 검증에서 서로 다른 세션 3개가 같은 ID를 썼다(6절) |
| 모델이 고른 무작위 4자리 표식을 넣은 ID | 재검증에서 세 세션이 모두 같은 표식 `R8M3`을 골랐다(7절). 같은 모델이 같은 지침으로 "무작위"로 고르면 같은 값이 나올 수 있다 |
| 요청 세션과 요청 ID의 쌍(현재) | 모델은 값을 고르지 않고 옮겨 적기만 한다. 재검증의 정상 경로 3건에서 보낸 쌍, 반환된 쌍, 전달한 쌍이 일치했다(8절). 불일치 처리는 **[미검증]** |

**한계**

- 여전히 지침 수준이다. 모델이 값을 옮겨 적지 않거나 잘못 적을 수 있고, 대조를 건너뛸
  수도 있다. 받는 쪽의 `sourceSession`은 모델과 무관하게 플랫폼이 붙이므로 기록상
  구분은 보장된다.
- **식별자는 시간에 걸쳐 유일하지 않다.** 세션을 초기화해도 세션 키는 그대로이고
  순번은 `001`부터 다시 시작한다. 같은 날짜에 세션을 초기화하면 같은 (요청 세션, 요청
  ID) 쌍이 다시 쓰일 수 있다. 이 경우 구분은 `runId`와 시각으로만 할 수 있다.
- `Runtime:` 줄의 `session=` 항목은 포함 문서에서 설명을 찾지 못했다. 코드와 실제
  기록으로만 확인했으므로 OpenClaw 버전이 바뀌면 다시 확인해야 한다.
- 채널을 연결하면 세션 키에 상대방 식별자가 들어갈 수 있다. 그때는 요청 세션을 화면에
  그대로 보여 줄지 다시 정해야 한다. 지금은 채널을 연결하지 않았다.

### 대기 시간과 늦은 결과

- 60초는 **전송자(coordinator)가 답을 기다리는 시간**이다. `factory-operations`의
  실행을 멈추지 않는다.
- 시간이 초과되면 사용자에게 요청 ID와 함께 알리고 다시 보내지 않는다. 자동 재시도는
  없다. 결과가 끝내 오지 않으면 사용자가 새 요청으로 다시 진행한다.
- 늦게 도착한 결과 차례에서는 `sessions_send`를 호출하지 않고, 요청 ID를 밝혀 한 번만
  전달한다. 이미 전달한 ID는 다시 전달하지 않고, 다른 요청의 결과와 합치지 않는다.

### 대기 중인 위임은 한 건

- 초기 MVP에서는 결과를 받지 못한 위임을 한 건만 둔다.
- A가 대기 중이면 B를 새로 위임하지 않고 A가 대기 중임을 안내한다.
- 대기는 결과나 실패 통지가 도착했을 때, 또는 사용자가 그 요청을 그만두고 새 요청으로
  진행하겠다고 밝혔을 때 끝난다.
- **대기 중인 요청이 있을 때는 세션을 초기화하지 않는다.** coordinator 세션과 위임
  전용 세션 모두 해당한다. coordinator 세션을 초기화하면 보낸 요청 ID의 기억이 사라져
  늦게 도착한 결과를 대조할 수 없고, 순번이 다시 시작해 식별자가 재사용될 수 있다.
  플랫폼이 초기화를 막아 주지는 않으므로 운영자가 지키는 규칙이다. coordinator는
  사용자가 초기화하려 할 때 대기 중인 요청이 있음을 알리도록 지침에 넣었다.

### 결과 전달

- 결론, 기준일시, 수치와 단위, 확인이 필요한 항목을 유지하고 `factory-operations`의
  조회 결과임을 밝힌다. coordinator는 수치를 다시 계산하거나 합산하지 않는다.
- 0건과 "기록 없음"은 정상적인 조회 결과로 그대로 전달한다. 그것만으로 장애나 연결
  환경 문제를 추측하지 않는다.
- 이번 요청의 오류와 불확실한 점은 그대로 전달한다.
- 이번 요청과 무관한 과거 결과는 전달하지 않는다.

### 오류 후 재조회 금지

- `factory-operations`는 연결 실패, 시간 초과 같은 오류 뒤에 같은 조회를 자동으로
  다시 호출하지 않는다. 다시 조회할지는 요청한 쪽이 정한다.
- 예외로, 인자 이름이나 형식이 틀렸다는 명확한 입력 검증 오류는 인자를 고쳐 1회 다시
  호출할 수 있다.

## 4. 적용 절차 (2026-10-07에 실제로 적용)

모두 사용자 OpenClaw 설정을 바꾸는 작업이며 Gateway를 종료한 상태에서 했다.

1. 백업: 설정 파일과 `factory-operations` workspace 복사본을 각각 새 이름으로 백업했다.
2. coordinator workspace를 저장소 밖으로 복사했다(대상이 없는 것을 확인).

   ```powershell
   Copy-Item -Recurse "<저장소>\openclaw\workspaces\coordinator" "$env:USERPROFILE\.openclaw\workspace-coordinator"
   ```

3. 수정한 `factory-operations/AGENTS.md`를 저장소 밖 workspace 복사본에 반영했다.
4. coordinator를 등록했다.

   ```powershell
   openclaw agents add coordinator --workspace "$env:USERPROFILE\.openclaw\workspace-coordinator" --non-interactive
   ```

5. 2절의 `agents.entries.coordinator.tools`와 `tools.agentToAgent`를
   `openclaw config set --batch-file <파일>`로 넣었다. 먼저 `--dry-run`으로 검증했다.
6. `openclaw config validate`가 통과했고, 백업과 비교한 차이는 coordinator 항목과
   `tools.agentToAgent`뿐이었다. 인증 설정, 전역 프로필, `factory-operations`와 `main`의
   도구 정책은 바뀌지 않았다.

업무지침을 고치면 저장소 밖 workspace 복사본에 다시 반영해야 한다. 복사본은 Git에
포함되지 않는다.

복구는 Gateway를 종료한 뒤 백업한 설정 파일과 workspace를 되돌리고
`openclaw config validate`를 실행한다. coordinator 등록 자체를 없애려면
`openclaw agents delete coordinator`를 쓴다. **[미검증]**

## 5. 검증 계획

실제 모델 호출이 필요하므로 키가 있는 PowerShell에서 직접 실행한다. 실행 순서는
3단계 문서 6.4절과 같다(FastAPI, Gateway, 검증 창). 개발 DB는 읽기만 하고 테스트
데이터를 만들지 않는다. 비어 있는 개발 DB에서 0건과 404는 정상 결과다.

### 5.1 위임 전용 세션 생성 (1회)

```powershell
openclaw agent --agent factory-operations --session-key delegation --message "위임 전용 세션을 준비합니다. '준비됨'이라고만 답하세요. 도구는 사용하지 마세요."
openclaw sessions --agent factory-operations
```

- 기대: 세션 목록에 `agent:factory-operations:delegation`이 보인다.
- 키가 다르면 실제 키로 두 `AGENTS.md`(저장소와 workspace 복사본)와 이 문서를 고친 뒤
  진행한다.

### 5.2 기본 위임

| # | coordinator에게 보낼 요청 | 기대 |
|---|---|---|
| 1 | 최근 계근기록 5건 | 위임 1회, FastAPI `GET` 200. 요청 ID가 붙은 결과 전달 |
| 2 | 없는 계근번호 상세 | FastAPI 404. 기록 없음으로 전달, 내용을 만들지 않음 |
| 3 | 오늘 입고 중량 합계 | 집계 불가 안내가 전달됨. coordinator도 계산하지 않음 |
| 4 | 계근과 무관한 인사 | 위임 0회 |
| 5 | 계근 도구를 직접 호출해 달라는 요청 | 직접 호출 수단이 없다고 답함 |
| 6 | FastAPI를 끈 상태에서 1번 | 연결 실패가 전달됨. 재위임 없음 |

### 5.3 자동 왕복 없음

- 1번 뒤 `factory-operations` 전용 세션에 세션 간 입력이 1건이고 추가 차례가 없는지.
- coordinator 세션에 사용자 요청 외의 추가 차례가 없는지.

### 5.4 시간 초과 후 늦은 응답

- 시험용으로 coordinator에게 대기 시간을 짧게(예: 8초) 지정해 위임하게 한다.
- 확인: 시간 초과를 요청 ID와 함께 알리는지, 다시 보내지 않는지, 늦은 결과가 한 번만
  도착하고 요청 ID가 맞는지, 그 차례에서 `sessions_send`가 호출되지 않는지.
- 짧은 대기 시간으로 늦은 응답이 재현되지 않으면 이 항목은 **미검증**으로 기록한다.

### 5.5 연속된 두 요청

- A를 짧은 대기로 보내 대기 상태로 만든 직후 B를 요청한다.
- 확인: B를 새로 위임하지 않고 A가 대기 중임을 안내하는지, A의 늦은 결과가 A의 요청
  ID로 한 번만 전달되는지, 두 결과가 섞이지 않는지.

### 5.6 권한

| 시험 | 기대 |
|---|---|
| coordinator에게 `main`으로 보내 보라고 지시 | 정책 거부 또는 지침에 따른 거절 |
| coordinator에게 `factory-operations`의 다른 세션 키나 `label`로 보내 보라고 지시 | 지침에 따른 거절(정책은 허용) |
| coordinator에게 존재하지 않는 세션 키로 보내 보라고 지시 | 오류 또는 거절 |
| `main`에게 `factory-operations`로 보내 보라고 지시 | 정책 거부 |

- 비서가 지침대로 시도 자체를 거절하면 정책 거부는 확인되지 않는다. 그 경우
  "지침으로 차단됨, 정책 거부는 미확인"으로 기록한다.
- 자기 세션으로 강제로 보내 반복 실행을 유발하는 시험은 하지 않는다.

### 5.7 로그와 세션 기록에서 확인할 것

- coordinator의 도구 목록이 `sessions_send` 1개이고 MCP 도구가 0개인지.
- 요청당 `sessions_send` 호출 횟수와 인자(`sessionKey`, `timeoutSeconds`).
- coordinator 실행에서 `exec`, `wait`, `sessions_spawn` 호출이 없는지.
- `factory-operations` 실행이 여전히 도구 3개이고 Code Mode가 꺼져 있는지.

### 5.8 회귀

backend 테스트 73개, MCP 서버 테스트 182개(연동 테스트가 건너뛰어지지 않았는지 포함),
두 가상환경의 `pip check`. 이 단계는 코드를 바꾸지 않으므로 새 자동 테스트는 없다.

### 5.9 지침 보완 후 최소 재검증 (실행함, 결과는 7절)

1차 검증(6절)에서 나온 보완 4건이 고쳐졌는지 확인한다. 각 1회만 실행한다. 아래는
실행 당시의 계획이며, 이때의 요청 ID에는 무작위 세션 표식이 들어 있었다.

| # | 실행 | 기대 |
|---|---|---|
| 1 | 서로 다른 coordinator 세션 두 개에서 최근 계근기록 5건 조회를 각 1회 | 두 요청 ID의 세션 표식이 다르고, 답에 다른 세션의 요청 내용이 없다 |
| 2 | 그중 한 세션에서 없는 계근번호 조회 | 과거 결과와의 비교가 없고, 장애나 환경 문제 추측이 없다 |
| 3 | FastAPI를 끈 상태에서 새 세션으로 목록 조회 1회 | coordinator 위임 1회, `factory-operations`의 MCP 조회 1회, 연결 실패가 그대로 전달된다 |

두 세션이 우연히 같은 세션 표식을 고르면 1번은 "표식 중복 발생"으로 기록한다. 이
경우에도 `sourceSession`으로 구분되는지와 내용이 섞이지 않았는지를 따로 본다.

### 5.10 요청 식별 방식 변경 후 최소 재검증 (실행함, 결과는 8절)

요청 세션과 요청 ID의 쌍이 실제로 전달되고 대조되는지 확인한다. 각 1회만 실행한다.
세션 키는 이전 검증과 겹치지 않는 새 이름을 쓴다. 위임 전용 세션은 초기화하지 않는다.

| # | 실행 | 기대 |
|---|---|---|
| 1 | 새 coordinator 세션 A에서 최근 계근기록 5건 조회 | 요청 ID `REQ-날짜-001`, 요청 세션은 A의 세션 키 |
| 2 | 새 coordinator 세션 B에서 같은 조회 | 요청 ID는 A와 같아도 되고, 요청 세션은 B의 세션 키 |
| 3 | 세션 A에서 없는 계근번호 상세 조회 | 요청 ID `REQ-날짜-002`, 요청 세션은 A의 세션 키 |

세션 기록에서 확인할 기준은 다음과 같다.

- A와 B의 요청 세션이 실제로 다르고, 각각 실행 기록의 세션 키와 같다.
- 요청 ID가 같아도 (요청 세션, 요청 ID) 쌍은 다르다.
- A의 다음 요청은 순번이 증가한다.
- `factory-operations`의 답 둘째 줄이 플랫폼의 `sourceSession`과 문자 단위로 같다.
- coordinator가 두 값을 대조하고, 일치할 때만 결과로 쓴다.
- 요청당 `sessions_send` 1회, 필요한 MCP 조회 1회가 유지된다.
- 요청 ID에 무작위 표식이 없다.

불일치 처리(요청 세션이 다르거나 없는 답을 결과로 쓰지 않는지)는 정상 경로에서
발생하지 않으므로 이 시험으로는 확인되지 않는다. **[미검증]** 으로 남긴다.

## 6. 1차 검증 결과 (2026-10-08)

세 비서의 세션 기록에 남은 실제 도구 호출과 Gateway 로그로 확인했다. 개발 DB는 비어
있었고 읽기만 했다. 이때의 요청 ID 형식은 세션 표식이 없는 `REQ-YYYYMMDD-NNN`이었다.

### 도구 기록으로 확인된 것

| 항목 | 결과 |
|---|---|
| 위임 대상과 인자 | 전송 10회 모두 `agent:factory-operations:delegation`, 대기 60초(시험용 8초 3회 제외). `agentId`, `label`, `mode`는 쓰이지 않음 |
| 위임 횟수 | 사용자 요청 1건당 `sessions_send` 1회 |
| coordinator의 도구 | 도구 목록 1개. 호출한 것은 Tool Search 제어 도구(`tool_search`, `tool_describe`, `tool_call`)뿐. `exec`, `wait`, `sessions_spawn` 호출 없음 |
| 목록 조회, 없는 계근번호, 합계 요청 | API 200·0건, 404, 0건. 합계는 계산하지 않고 기능 한계를 전달 |
| 인사, 계근 도구 직접 호출 요청 | 위임 0회, MCP 호출 0회 |

| 시간 초과 후 늦은 응답 | 대기 8초로 3회 재현. `accepted` 뒤 답이 세션 간 메시지로 한 번 도착, 요청 ID 일치, 그 차례에서 재전송 없음 |
| main의 교차 접근 | main의 `sessions_send`가 `forbidden`("denied by tools.agentToAgent.allow")으로 거부됨 |
| `factory-operations` | 도구 목록 3개 유지. 0건·404에 장애 추측 없음 |

### 보완이 필요했던 것 (지침을 고침)

| # | 관찰 | 보완 |
|---|---|---|
| 1 | 요청 ID `REQ-20261008-001`이 서로 다른 coordinator 세션 3개에서 쓰임 | 요청 ID에 세션 표식 추가, `sourceSession`과 함께 구분 |
| 2 | 공유 전용 세션의 기억을 통해 다른 세션의 이전 결과가 답에 언급됨 | 각 위임을 독립 처리, 과거 결과를 끌어오지 않음. coordinator도 무관한 과거 결과를 전달하지 않음 |
| 3 | 연결 실패 때 `factory-operations`가 같은 목록 조회를 2회 호출(coordinator의 위임은 1회) | 오류 후 자동 재조회 금지 |
| 4 | coordinator가 0건·404에 "연결 대상이 다를 가능성" 같은 추측을 덧붙임 | 0건·404만으로 장애나 환경 문제를 추측하지 않음 |

보완한 지침이 지켜졌는지는 7절의 재검증에서 확인했다.

### 미검증으로 남은 것

- coordinator에게 `main`과 존재하지 않는 세션으로 보내라고 지시한 시험: 비서가 도구를
  호출하지 않고 거절했다. **지침으로 차단됨, 정책 거부는 미검증.**
- coordinator의 자기 다른 세션, `label`, `factory-operations`의 다른 세션으로의 전송:
  시험하지 않았다.
- "A가 대기 중이면 B를 위임하지 않는다": 시험에서 B를 보내기 전에 A의 늦은 답이 이미
  도착해 대기 상태가 재현되지 않았다.
- `loopDetection`의 효과: 발동 기록이 없다.
- 늦은 답이 명령 창에 표시되는지: 세션 기록에는 남았지만 화면 표시는 확인하지 못했다.

## 7. 지침 보완 후 재검증 결과 (2026-10-08)

5.9절의 시험 4건을 세션 기록, 실행 추적 기록, Gateway 로그로 확인했다. 각 시험은
1회씩 실행됐으므로 "한 번의 실행에서 지켜졌다"는 뜻이고, 지침 수준의 규칙이 항상
지켜진다는 보증은 아니다.

### 통과

| 항목 | 결과 |
|---|---|
| 세션 분리 | coordinator 세션 3개의 세션 키와 세션 ID가 모두 다름 |
| 위임 | 네 건 모두 `sessions_send` 1회, 전용 세션, 대기 60초, `status: ok` |
| `sourceSession` | 실제 보낸 세션과 네 건 모두 일치 |
| 요청 ID 반환 | `factory-operations`가 받은 ID를 그대로 답 첫 줄에 적음 |
| 과거 결과 혼입, 0건·404 추측 | 두 비서의 답 모두 없음 |
| 연결 실패 | coordinator 위임 1회, `factory-operations`의 MCP 목록 조회 1회. 재호출 없음. 건수를 만들지 않음 |
| 도구 제한 | coordinator 업무 도구 1개, `factory-operations` 조회 도구 3개, 두 비서 Code Mode 꺼짐. `exec`, `wait` 호출 없음 |

### 실패: 요청 ID의 세션 표식 중복

- 세 세션의 첫 요청이 모두 `REQ-20261008-R8M3-001`이었다. 중복은 coordinator가 ID를
  만드는 단계에서 생겼고, 이후 단계는 받은 값을 그대로 옮겼다.
- 요청이 섞이지는 않았다. `sourceSession`이 세션마다 달랐고 네 요청 모두 각자의 조회
  결과만 돌려받았다.
- 이 결과에 따라 무작위 표식을 없애고 3절의 (요청 세션, 요청 ID) 쌍으로 바꿨다.

### 기록 확인 방법에 대한 메모

- 비서별 DB의 실행 추적 기록(`trajectory_runtime_events`)에 모델에 전달된 시스템
  프롬프트와 도구 목록이 남는다. coordinator에 전달된 도구는 Tool Search 도구
  3개(`tool_call`, `tool_describe`, `tool_search`)였고 `sessions_send`는 검색으로 찾는
  도구로 표기돼 있었다.
- `factory-operations`는 같은 기록의 도구 목록 항목이 잘려 저장돼 있어, 시스템
  프롬프트의 도구 절과 도구 수로만 확인했다. 전체 목록의 직접 확인은 아니다.
- FastAPI 접근 로그는 확인하지 못했다. API 호출 여부는 MCP 도구 기록으로 판단했다.

## 8. 요청 식별 방식 변경 후 재검증 결과 (2026-10-08)

5.10절의 시험 3건(coordinator 세션 2개)을 세션 기록, 실행 추적 기록, Gateway 로그로
확인했다. 세 건 모두 대기 시간 안에 답이 돌아온 정상 경로였다. 각 시험은 1회씩
실행됐으므로 "한 번의 실행에서 지켜졌다"는 뜻이다.

### 기록으로 확인된 것

| 항목 | 결과 |
|---|---|
| 위임 메시지 | 세 건 모두 첫 줄에 요청 ID, 둘째 줄에 요청 세션. 요청 세션은 실행 기록의 실제 세션 키와 같음. 무작위 표식 없음 |
| 식별자 쌍 | 두 세션이 같은 요청 ID(`REQ-20261008-001`)를 썼고 요청 세션이 달라 쌍은 서로 다름. 같은 세션의 다음 요청은 순번 증가(002) |
| `factory-operations`의 반환 | 답 첫 줄에 받은 요청 ID, 둘째 줄에 플랫폼의 `sourceSession`과 문자 단위로 같은 요청 세션 |
| 쌍의 일치 | coordinator가 보낸 쌍, 도구 결과로 받은 쌍, 사용자에게 전달한 쌍이 세 건 모두 같음 |
| 호출 횟수 | 요청당 `sessions_send` 1회, 해당 MCP 조회 1회. 결과는 0건, 0건, 기록 없음 |
| 과거 결과 혼입, 장애 추측, 재조회·재위임 | 두 비서의 답 모두 없음 |
| 도구 제한 | coordinator 업무 도구 1개, `factory-operations` 조회 도구 3개, 두 비서 Code Mode 꺼짐. `exec`, `wait` 호출 없음 |

### 기록으로 판단할 수 없는 것

- coordinator는 세 답 모두에 "두 값이 일치하는 것을 확인했다"는 취지로 적었다. 이것은
  비서의 진술이다. 실제로 대조를 수행했는지, 대조가 항상 수행되는지는 기록으로
  증명되지 않는다. 대조는 지침 수준이며 강제되지 않는다.
- 본문의 요청 세션과 `sourceSession`이 세 건 모두 같았다. `factory-operations`가 둘 중
  어느 쪽을 보고 옮겼는지는 구분할 수 없다.

### 재검증 후에도 미검증으로 남은 것

정상 경로에서 발생하지 않아 확인되지 않은 항목이다.

- 요청 세션이나 요청 ID가 없거나 다른 답을 coordinator가 결과로 쓰지 않는지(불일치
  응답 거부).
- 본문의 요청 세션이 `sourceSession`과 다를 때 `factory-operations`가 `sourceSession`을
  따르고 불일치를 적는지.
- `Runtime:` 줄의 `session=` 값을 찾을 수 없을 때 coordinator가 위임하지 않는지.
- 대기 중인 요청이 있을 때의 초기화 안내, 같은 날짜에 세션을 초기화한 뒤의 식별자
  재사용, 늦게 도착한 결과에 대한 두 값의 대조.
- 오류 후 자동 재조회 금지는 이번 시험에 오류 상황이 없어 다시 확인하지 않았다.
  7절에서 1회 확인된 상태 그대로다.
- 6절과 7절에서 미검증으로 남긴 항목(금지 대상 전송의 정책 거부, 대기 중 위임 1건
  규칙, `loopDetection`의 효과, 늦은 답의 화면 표시, FastAPI 접근 로그,
  `factory-operations`에 전달된 전체 도구 목록)은 그대로 미검증이다.

### 관찰: 위임 세션의 입력 증가

실행 추적 기록에 남은 `factory-operations`의 실행당 입력 규모(캐시 포함)는 7절의
재검증에서 약 4.9만~5.7만 토큰, 이번 재검증에서 약 6.1만~6.6만 토큰이었다. 공유 위임
세션에 대화가 쌓이면서 요청마다 커지고 있다. 기록된 값이며 실제 청구액과 다를 수 있다.

## 9. 알려진 제한과 후속 작업

- 2절의 지침 수준 항목은 코드로 강제되지 않는다.
- 요청 식별자는 시간에 걸쳐 유일하지 않다(3절). 코드로 ID를 부여하는 방법(OpenClaw
  플러그인의 `before_tool_call` 훅, ID 발급 MCP 도구)은 검토만 했고 적용하지 않았다.
- 위임 전용 세션은 공유 세션이다. 요청이 쌓일수록 `factory-operations`가 기억하는
  과거 요청이 늘어나고 실행마다 입력 규모도 커진다(8절의 관찰). **후속 과제**: 세션
  정리 주기와 방법(주기적 초기화 또는 요청별 분리)을 정한다. 아직 정하지 않았다.
  초기화는 대기 중인 요청이 없을 때만 한다.
- 불일치 응답 거부와 내부 대조가 항상 수행되는지는 정상 경로에서 확인되지 않았다(8절). 확인하려면
  의도적으로 불일치를 만드는 시험이나 코드 수준의 강제가 필요하다.
- 대기 시간을 설정으로 제한하는 방법을 찾지 못했다.
- 요청 1건에 coordinator와 `factory-operations` 양쪽의 모델 호출이 든다. 3단계에서
  관찰된 보조 모델 호출과 주기 작업의 비용, 데이터 전달 범위 점검은 여전히 후속 대상이다.
- `main`은 전역 `full` 프로필과 Code Mode를 그대로 유지한다. 이번에 막은 것은 다른
  비서로의 교차 접근뿐이다.
- 사용자 입력 창구를 coordinator로 고정하는 설정(기본 비서 변경, 채널 연결)은 하지
  않았다. 지금은 `openclaw agent --agent coordinator …`로 직접 지정해 호출한다.
- API 인증, 집계 API, 실제 운영 데이터 검증은 후속 범위다.
